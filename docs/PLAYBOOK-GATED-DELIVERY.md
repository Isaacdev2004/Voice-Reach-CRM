# Gated playbook delivery

The playbook is a lead magnet. It is not available through a public download link.

On explicit submission, `/api/marketing/playbook` validates a nonempty name, valid email and request UUID. It reads the private PDF, then sends contact information to the existing configured MyARI support mailbox. Only after Resend returns an accepted receipt does it submit the requested PDF attachment to the prospect. The response never contains the PDF or a download URL. Acceptance means queued with the provider, not confirmed inbox delivery. This captures leads in the existing mailbox workflow, not a new CRM database table.

`RESEND_API_KEY` and `RESEND_FROM_EMAIL` must be configured with an authorized sender. Missing configuration returns a safe unavailable response. Provider failures, empty acknowledgements and timeouts never return success. Request-specific provider idempotency keys reduce duplicate capture/delivery on retries; their scope follows Resend's retention window. Contact details and provider responses are not logged. The request does not authorize unrelated marketing.

The PDF lives in `resources/`, outside `public/`. Next output tracing includes it only as a server dependency. Its source is existing MyARI educational articles, generated by `scripts/build-private-playbook.cjs`. No public GET/download handler is implemented.

Tests: `node scripts/public-playbook.test.cjs` uses synthetic details and mocked providers, covering invalid/blank details, capture-before-delivery, private attachment, capture/delivery failures, missing configuration, malformed provider acknowledgement and timeout. No real emails sent. Production sender configuration and real inbox delivery remain unverified.
