# Concierge infrastructure audit

Baseline: e409de41304e06e908643309d17d45c1e1bca913. Audit is repository inspection plus read-only restored-test schema inspection; no Production changes.

Verified in code: Clerk requireUserId is the authoritative owner_id; there is no verified Clerk-org tenant model. Registration uses existing Clerk pages; billing/trials remain existing Stripe/settings infrastructure. Do not create a second subscription source. Saved settings use owner-filtered audit_logs SETTINGS_SAVED. Brand Kit and existing Settings onboarding panel exist. Existing contact import reuses PapaParse/phone normalization but immediately inserts, has no reviewed preview/replay workflow, and can infer affirmative consent from CSV values. Concierge uses the same parser in a separate approval-bound import path, forces Unknown consent and dnc suppression, never updates existing contacts. Legacy importer remains unchanged; its separate limitations must not be described as fixed globally.

Existing original templates are preserved. Concierge reuses the separate reviewed premium draft catalog and existing builder service with action=template, provider=mock, and no enrollment parameters. Starter CRM capability limits are retained. Commercial and relationship/referral/review premium drafts already exist and are reused. Several other requested campaign categories are not in the existing catalog; those are not advertised as implemented. Assistant chat/approved proposals exist behind owner entitlements; unsaved drafts can be revised, saved campaigns require existing editor. New Concierge never enables Assistant or spends AI automatically.

Existing administrative AI usage view uses explicit environment allowlists, not a general support role system. Concierge adds its own least-privilege operational case roles without granting contact/credential access or impersonation. Admins/managers see only explicitly eligible cases; specialists see assigned cases; sales see assigned operational status only. Team-role collaboration is not inferred from profile answers. Existing actual CRM plan/seat rules continue to apply.

Existing provider/status endpoints report credential/config presence; these are not proof of connectivity. Calendar status distinguishes OAuth authorization from verified sync. Settings onboarding performs live verification but can fail entirely when optional financing tables are absent. Concierge links to those existing verification flows and represents configuration as verification pending, never connected based on env presence. No live communications used. Sapphire voice requires existing provider verification and approved assets; no new voice provider invented.

Restored staging has contacts, campaigns, campaign_steps, audit_logs, calendar_events; top-level tasks/notes tables are absent in that snapshot, so the Concierge case/training records do not assume those optional schemas exist. Financing Studio production readiness remains outside this work; link is guidance only, not an operational completion claim.

New durable storage: concierge_cases, concierge_events, concierge_imports. One migration, no existing CRM table alterations; only explicitly approved imports insert contacts and Unknown consent records atomically. New tables have RLS with no browser policies and revoked anon/authenticated privileges; service-role-only RPCs. This matches the existing Clerk + server-authorized service credential architecture. No unrestricted SQL tools or staff credentials UI.
